## v0.1.1 实施进展（2026-10-22）

下方差距表保留为本轮开发前的 v0.1 基线。现已补上英文默认与 `/zh`、SSR 国际化、双语错误与邮件、验证邮件重发、Google 条件接入、SEO 路由、命名 staging 隔离、私有写操作限流及隔离生产构建验收。详见 [本轮记录](../qa/acceptance-v0.1.1.md)。

仍需真实 Cloudflare 预发布、邮件收信、Google 账户回调与 Stripe 测试账户联调；账户删除、AI、文件、额度账本和管理增强未实现。后续已补本地初始化 CLI 与 Skill，仍没有云资源自动配置或自动升级。因此 v0.1.1 的海外上线目标尚未全部完成。

## 当前判断

技术栈基本对齐：TanStack Start、Cloudflare Workers/D1、Drizzle、Better Auth、shadcn/ui、Base UI。我们已具备本地认证、私有 CRUD、套餐限制和部分支付同步测试；仍属于本地基础版，尚不能称为 TanStarter 的完整开源替代。

主要差距是功能范围、供应商真实联调和跨项目交付经验。MIT、中文文档和 AI 规则已经具备，但还需要正式开源发布与真实项目使用来验证价值。不能用无依据的完成百分比、组件数或测试用例数代替比较。

## 推荐顺序

### 下一轮：v0.1.1，海外上线基础闭环

目标：在一个真实 HTTPS 预发布地址上，完成「注册/Google 登录 → 真正收信 → 登录 → 创建并保存项目 → Stripe 测试结账 → 权益同步 → 取消」流程。

交付范围：

1. 完整的英文默认与中英文国际化，刷新/直接访问保持语言，SSR 与浏览器一致；错误和验证/重置邮件可读。
2. 验证邮件重发与冷却/失败状态；Google OAuth；账户删除涉及订阅与数据处置时，先明确策略再实现。
3. 明确隔离开发与预发布数据/密钥；补本地生产构建 smoke，验证收件箱等开发入口在生产环境关闭。
4. 真实 Cloudflare/邮件/Stripe 测试联调，记录数据库状态和失败路径；上线运行指标、数据库恢复演练与基本业务限流。

本地代码与测试可以先完成；远端验收需要真实 Cloudflare/邮件域名、OAuth 和 Stripe 测试账户配置。此文档只是下一步建议，没有执行创建资源、开通付费、真实发信、建仓库或发布。保留 TEST ONLY 规则，正式支付另行设计与验收。

### 再下一轮：v0.2，一个 AI 产品闭环

先选一个能直接复用的小工具，例如文本整理/摘要。交付模型调用、流式 UI、历史、R2 私有文件、服务端额度账本和套餐限制。验收并发不超额、请求重试不重复结算、取消/超时有明确规则、刷新可恢复历史。

额度账本是我们针对 AI 工具提出的必要设计；未从本轮核对的 TanStarter 文档确认其有完整的预留/结算/释放账本，因此不把它列为对方已实现能力，也不宣称我们已形成独有优势。

### 随后：可反复使用的开源交付

创建正式开源仓库和可复现演示、维护发布记录、验证两个独立产品接入，再完善本地初始化命令、云端配置流程和升级说明。初始化应能替换品牌、域名与资源名，选择可选模块，并排除本地数据库、测试账户和秘密。当前没有第二个消费者，先不做插件平台、共享账号中心或多云抽象。

博客、Newsletter、客服、多个支付商、多模态模型大全和团队组织管理，按具体产品需要后置。是否加入缓存由真实查询和性能数据决定。

## 对外可用的表述

目前可以说「TanStack + Cloudflare 的 MIT 开源底座，本地身份/数据流程已验证，支付测试集成代码已提供」。尚不宜说「完整替代 TanStarter」「开箱即用正式收款」「全部生产可用」或「所有项目一键无痛升级」。
